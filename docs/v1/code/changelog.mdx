# Changelog

Cherry Styled Components is currently at version `0.3.0`. The entries below are based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

<Update label="0.3.0" description="2026-11-23">

Light and dark mode now switch through CSS variables. The theme your components see is one object for both modes, whose colors and shadows are `var(--cherry-...)` references, and the mode is a `dark` class on `<html>`. A switch flips the class and the browser repaints: no styled component renders again (538 re-renders and 921 CSS transitions per toggle on the demo page before, none now), and the page changes at once instead of fading control by control. Every component looks exactly as in 0.2.24 in both modes. See [Dark Mode](/v1/code/dark-mode) and [Theming through CSS variables](/v1/code/theme#theming-through-css-variables).

<Badge color="green" size="sm">Added</Badge>

- `createThemeVariables(theme, themeDark?)`: builds the CSS-variable theme, the stylesheet behind it (light values on `:root`, dark ones on `:root.dark`) and both resolved palettes. The providers call it for you; it is server-safe, for rendering the stylesheet or reading the palettes in server code. See [Theme](/v1/code/theme#createthemevariables)
- `useColorMode()`: the mode in force, the visitor's preference (`"light"`, `"dark"` or `"system"`), `setPreference` and `toggleTheme`. Only components that call it render again when the mode switches. See [Hooks](/v1/code/hooks#usecolormode)
- `useResolvedTheme()`: the theme with real color values for the mode in force, plus `isDark`, for code that hands a theme color to something CSS does not style (a canvas, a JS color library, an editor theme). See [Hooks](/v1/code/hooks#useresolvedtheme)
- `modes()`: wraps a styled interpolation written against `theme.isDark` and emits CSS that follows the mode, so most existing `isDark` branches migrate by wrapping them: `${modes(({ theme }) => (theme.isDark ? theme.colors.gray : theme.colors.grayLight))}`. `modeValue(light, dark)` is the plain-CSS form. See [Dark Mode](/v1/code/dark-mode#styles-that-differ-by-mode)
- A "system" preference: visitors who never choose a mode follow the OS, live. An explicit choice is stored as `themePreference` in localStorage, and the mode in force is mirrored to the `theme` cookie
- `$mode` prop on both providers: pins a mode without storing anything (toggling does nothing while it is set)
- `colors.primaryFillHover`: an optional token for the hover shade of the solid primary fill
- `ThemeInitScriptOptions` type

<Badge color="blue" size="sm">Changed</Badge>

- **Breaking:** `Theme.isDark` is gone. Components receive one theme for both modes, so a style can no longer branch on the mode in JS; TypeScript now flags every `theme.isDark` read. Replace each one with a mode token (`accent`, `link`, `onFilled`, `primaryTint*`, `shadows.toast`), a `:root.dark &` rule, or `modes()`. Remove `isDark` from your own theme objects
- **Breaking:** theme colors and shadows are CSS variables inside styled components, so JS code that parses or computes with them (polished's `darken()`, `rgba()`, `readableColor()` and the like) gets `var(--cherry-color-primary)` instead of a hex value. Use the native `color-mix()` helpers `alpha`, `shade` and `tint`, or read real values from `useResolvedTheme()`
- **Breaking:** `ThemeContext` provides `{ toggleTheme, setPreference }`. `setTheme(themeObject)` is gone: call `setPreference("light" | "dark" | "system")`
- **Breaking:** `createThemeInitScript()` takes an options object, `{ themeColor?: { light, dark } | false }`, instead of `(darkBackground, darkThemeColor)`. The script now sets the `dark` class before the first paint on every load (not only the first visit), so it no longer hides the page or needs a background color. Keep rendering `themeInitScript` (or your own instance) in the document `<head>` of a server-rendered app
- `CherryThemeProvider` and `ClientThemeProvider` share one implementation and keep their props (`theme`, `themeDark`, `$themeColor`, `$globalStyles`). `$initial` now only sets the mode `useColorMode()` reports during the server render; the colors no longer depend on it. Without `themeDark` the page stays light
- The mode tokens (`accent`, `link`, `onFilled`, `primaryTintHover`, `primaryTintDrop`, `primaryTintActive`, `shadows.toast`) are always filled in per mode by the providers. `accentColor`, `linkColor`, `primaryTintColor` and `filledTextColor` read the tokens. See [Mixins](/v1/code/mixins#mode-token-helpers)
- The providers render the variables as a plain `<style data-cherry-theme>` element, outside styled-components, whose CSS preprocessor drops the empty custom properties `modeValue()` relies on
- A mode switch turns transitions off for the frame that paints it (`.theme-switching` on `<html>`), so colors change at once. The [ThemeToggle](/v1/code/theme-toggle) knob jumps instead of sliding for the same reason

<Badge color="red" size="sm">Removed</Badge>

- **Breaking:** `darkFilledTextRule` and `darkPrimaryTintRule`. The mode tokens they patched now always follow the mode: drop the calls and keep `filledTextColor` / `primaryTintColor`

<Badge color="purple" size="sm">Migrating from 0.2</Badge>

Your providers keep their `theme` and `themeDark` props. What changes is code that reads the mode or computes with theme colors:

1. Remove `isDark` from your own theme objects.
2. Replace every `theme.isDark` read in your styles with a mode token, a `:root.dark &` rule, or `modes()`:

```tsx
import styled from "styled-components";
import { modes } from "cherry-styled-components";

// Before: border-color: ${({ theme }) => (theme.isDark ? gray : grayLight)}
const Card = styled.div`
  border-color: ${modes(({ theme }) =>
    theme.isDark ? theme.colors.gray : theme.colors.grayLight,
  )};

  :root.dark & {
    outline: 1px solid ${({ theme }) => theme.colors.grayDark};
  }
`;
```

3. Replace JS color math on theme colors (`darken()`, `rgba()`, `readableColor()`) with `alpha`, `shade` and `tint`, or read real values from `useResolvedTheme()`.
4. Replace `setTheme(themeObject)` with `setPreference("light" | "dark" | "system")`.
5. Replace `createThemeInitScript(darkBackground, darkThemeColor)` with `createThemeInitScript({ themeColor: { light, dark } })`, or `{ themeColor: false }`. Keep the script in the `<head>` of a server-rendered app.
6. Drop `darkFilledTextRule` and `darkPrimaryTintRule` calls.
7. `$initial` now only affects `useColorMode()` during the server render. To force a mode, use `$mode`.

Visitors keep their choice: a `theme` entry in localStorage written by an earlier version counts as their explicit preference.

</Update>

<Update label="0.2.24" description="2026-11-18">

<Badge color="green" size="sm">Added</Badge>

- [Toast](/v1/code/toast): a redesigned card. A colored icon tile whose glyph draws itself in once the card lands, a bold title, an optional `description` line, an optional `action` button (a small Cherry [Button](/v1/code/button) that runs `onClick` and then dismisses) and a close badge on the corner that shows on hover or focus (always on touch screens)
- [Toast](/v1/code/toast): two more colors. `"default"` has no icon tile, for plain messages like "Message archived"; `"loading"` shows the [Spinner](/v1/code/spinner) and never hides itself
- [Toast](/v1/code/toast): a collapsed deck. The newest toast sits in front and older ones peek out behind it, smaller, with their content hidden. Hovering, focusing or tapping the stack fans it out and pauses auto-hide, which also pauses while the tab is hidden. Swipe a toast toward its edge or sideways to dismiss it, or press Escape while it has focus
- `ToastNotifications` props `$expand` (keep every toast fanned out, the old list look) and `$visibleToasts` (how many show at once, default `3`)
- `useToastNotifications()` returns `updateNotification(id, update)` to change a toast in place, `dismissNotification(id)` to remove one with its exit animation, and `promiseNotification(task, { loading, success, error }, config?)`, which shows a loading toast and swaps it to success or error when the promise settles (settled toasts hide after 4 seconds unless `autoHide` says otherwise)
- `ToastConfig` gains `description`, `action`, `dismissible` (close badge and swipe, default `true`) and `id` (reuse an id to replace that toast in place). New exported types: `ToastAction`, `ToastUpdate`, `ToastPromiseMessages`, `ToastNotification`
- `ThemedGlobalStyles`: Cherry's global styles as one component that reads the active theme from the `ThemeProvider`. See [Global Styles](/v1/code/global-styles)

<Badge color="blue" size="sm">Changed</Badge>

- `addNotification` returns the new toast's id
- A toast's text is typed `React.ReactNode` instead of `string`. Existing calls are unaffected
- The toast stack is a fixed-width column (`min(380px, 100vw - 40px)`) anchored by `$align` and `$bottom`, instead of a full-width strip of pills

<Badge color="orange" size="sm">Fixed</Badge>

- `CherryThemeProvider` and `ClientThemeProvider` no longer crash in development with "Rendered fewer hooks than expected". Since 0.2.23 they built the global style component inside `useMemo`, and styled-components' development build calls a hook whenever a styled component is created, which React rejects there. Both providers now render the module-level `ThemedGlobalStyles`. Production builds were not affected

</Update>

<Update label="0.2.20" description="2026-10-23">

<Badge color="green" size="sm">Added</Badge>

- [Modal](/v1/code/modal)s stack. A modal opened over an open one (a "confirm with a code" step over a form, say) no longer shows on top of it: the open modal's card sinks out first, then the new card rises in over the same backdrop, and closing the top one plays it backwards. The modal underneath stays mounted while it is covered, so whatever was typed in it is still there when it comes back, and it ignores <kbd>Esc</kbd> and clicks outside, which belong to the modal on top. Before, both cards showed at once, and a click inside the top modal counted as a click outside the one under it, which closed it
- `$stack` on `Modal` (default `true`). Pass `$stack={false}` to keep the previous behaviour for that modal: it neither hides the modals under it nor steps aside for the ones opened over it
- `useModalLayer(open)` puts a full-page layer that is not a `Modal` (an outage screen, a sign-in wall) on the same stack while `open`: an open modal fades away under it and comes back once it is gone. Returns whether another layer covers it. See [Hooks](/v1/code/hooks)

</Update>

<Update label="0.2.17" description="2026-09-06">

<Badge color="green" size="sm">Added</Badge>

- `Icon` takes an `icon` prop: an imported Lucide component, `import { ArrowRight } from "lucide-react"` then `<Icon icon={ArrowRight} />`. It costs exactly that glyph, tree-shakes, and renders on the server. The prop is typed `IconComponent`, any component that accepts `IconGlyphProps` (`size`, `color`, `className` and the aria attributes), so a custom SVG component or another icon set works as well. See [Icon](/v1/code/icon)
- `cherry-styled-components/dynamic` subpath exporting `DynamicIcon`, for an icon chosen at runtime (CMS content, user settings): `<DynamicIcon name="arrow-right" />` resolves the name on demand through `lucide-react/dynamic`, accepts Lucide's PascalCase export name or kebab-case id, and renders nothing for an unknown name. The glyph appears after hydration and never in server-rendered HTML. Only apps that import the subpath carry Lucide's dynamic import map, which bundlers turn into one small chunk per icon; nothing on the main entry references it. Also exports `IconName`, the accepted names, and `DynamicIconProps`
- `IconSource` (`IconComponent | ReactElement`, what `$icon`-style props accept) and `renderIcon(source, props)` (renders one, for components that forward such a prop) are exported. [Avatar](/v1/code/avatar), [AvatarDropzone](/v1/code/avatar-dropzone) and [Dropzone](/v1/code/dropzone) (`$icon`), [Callout](/v1/code/callout) (`$icon`), [ChatPanel](/v1/code/chat-panel) (`$titleIcon`) and [Spinner](/v1/code/spinner) (`icon`) take an imported component, which they size, or a rendered element, used as given, so a runtime-chosen icon is `$icon={<DynamicIcon name={n} />}`

<Badge color="blue" size="sm">Changed</Badge>

- <Badge solid color="error" size="sm">Breaking</Badge> `<Icon name="...">` is gone from the main entry; `Icon` renders only an `icon` component. Move every call site to `icon={ImportedGlyph}`; for a name that comes from data, import `DynamicIcon` from `cherry-styled-components/dynamic`. The `$icon`-style props above no longer accept a string, and `Spinner` drops `name`. `IconProps` is now the props interface of `Icon`, as on every other component; the name union it used to be lives on as `IconName` in the `/dynamic` subpath
- <Badge solid color="error" size="sm">Breaking</Badge> `lucide-react` is a peer dependency instead of a dependency. Apps import glyphs from it themselves now, so install it alongside Cherry (see [Installation](/v1/code/installation)); one copy shared by the app and the library keeps every glyph bundled once
- Every internal component imports the glyphs it draws straight from `lucide-react`: `X` for Modal and Toast, `ChevronDown` for Select and Accordion, `Sun` and `MoonStar` for ThemeToggle, and so on. Until now the shared `Icon` did `icons[name]` over the full Lucide map, so mounting any Select, Modal, Toast, Input, Spinner or ThemeToggle shipped all 1,800 icons, roughly 500 KB (133 KB gzipped), on every page of every consumer whatever the app itself imported. The demo app's entry bundle drops from 864 KB to 355 KB
- `tsconfig.json` sets `module` to `ESNext` (was `ES6`); the published output is unchanged

</Update>

<Update label="0.2.16" description="2026-08-14">

<Badge color="blue" size="sm">Changed</Badge>

- <Badge solid color="error" size="sm">Breaking</Badge> `StyledComponentsRegistry` now ships from the `cherry-styled-components/next` subpath instead of the package root. <Badge color="orange" size="sm">Fixed</Badge>

- `useOnClickOutside` (and with it [Modal](/v1/code/modal)): a mousedown that no user press can account for is no longer read as a click outside while a native OS picker is engaged. iOS draws the pickers behind `<select>` and `<input type="date|datetime-local|month|time|week">` outside the web view, so the taps that drive them never reach the DOM; when the picker resolves, WebKit still emits a stray mousedown whose target sits outside the component, which dismissed the entire dialog the moment a user set a date inside a `Modal` on iPhone. The hook now records genuine presses (`pointerdown`/`touchstart`, capture phase, one shared listener set for all instances) and ignores events that arrive with no press behind them while such a control holds focus or gave it up within the last 400ms. Backdrop taps, the close button, <kbd>Esc</kbd>, and clicks inside behave exactly as before

</Update>

<Update label="0.2.12" description="2026-07-30">

<Badge color="green" size="sm">Added</Badge>

- New `alpha(color, percent)`, `shade(color, percent)`, and `tint(color, percent)` color helpers, exported from the package root. `alpha` fades a color to `percent` opacity, `shade` darkens it `percent` toward black, and `tint` lightens it `percent` toward white. They return a native CSS `color-mix(in srgb, ...)` string rather than a computed hex, so the input can be any valid CSS color, including a `var(--token)` reference that only the browser can resolve.
